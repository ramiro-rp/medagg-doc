# Обзор продукта

**Medical Imaging Dataset Aggregator (MedAgg)** — MVP-система, которая помогает
находить и структурировать метаданные медицинских датасетов для ML.

Этот документ описывает продуктовую цель и текущий статус реализации.

> Интеграционное примечание (снапшот тестов): на данный момент система предоставляет
> каталог датасетов, детальные страницы датасета, и поиск по каталогу (локально).
> Подключение внешних источников и пользовательские коллекции — цели следующей итерации.

---

## 1. Проблема и контекст

В медицинском ML существует множество открытых наборов данных (Kaggle, TCIA и др.), но:

- данные разбросаны по разным платформам;
- форматы описаний и тегов не стандартизированы;
- поиск по модальности/органу/задаче неудобен;
- повторное использование датасетов затруднено.

MedAgg решает эту проблему, предоставляя единый каталог и API.

---

## 2. Целевая аудитория

- исследователи и студенты ML/Computer Vision;
- врачи и клиницисты, участвующие в исследованиях;
- команды, собирающие датасеты для обучения моделей.

---

## 3. Основные пользовательские сценарии (MVP)

### 3.1 Просмотр каталога

Пользователь открывает каталог, видит список датасетов и переходит на страницу деталей.

### 3.2 Поиск

Пользователь вводит текстовый запрос и/или применяет фильтры (орган, модальность, теги и т.п.).
Система возвращает результаты поиска.

---

## 4. Функциональные возможности

### 4.1 Реализовано в интеграционном снапшоте

- Backend API (Django + DRF):
  - `GET /api/v1/datasets/` — список;
  - `GET /api/v1/datasets/{id}/` — детали;
  - `POST /api/v1/search/datasets/` — поиск.
- PostgreSQL как основная БД.
- Frontend (Vite + React) потребляет API и отображает каталог/детали/поиск.

### 4.2 Частично реализовано

- Интеграция с внешним источником (например, Kaggle) может быть включена при наличии ключей.
  В тестах функциональность зависит от окружения и настроек.

### 4.3 Запланировано (следующая итерация)

- аккаунты пользователей и роли;
- «Мои датасеты» / сохранённые элементы;
- формирование пользовательских коллекций и экспорт (ZIP + metadata);
- полноценный админ-раздел во фронтенде (сейчас используется Django Admin);
- расширение источников (TCIA и др.) и синхронизация каталога.

---

## 5. Технический контур

- Frontend: SPA, переменная окружения `VITE_API_URL` указывает на базовый URL API.
- Backend: DRF, включает CORS настройки.
- БД: PostgreSQL; миграции управляются Django.

> Важно: контракт API возвращает `tags`, `modalities`, `ml_tasks` как массив объектов `{id, name}`.
> Фронтенд может отображать только `name`, но на уровне контракта это объектная структура.

---

## 6. Ограничения MVP

- развертывание в одном окружении (single-node);
- минимальный мониторинг;
- отсутствие полноценного потока пользовательских коллекций.
